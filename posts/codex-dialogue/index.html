和 Codex 做代码审查：测试全绿之后，还该看哪里

SLLYING2026.09.083 分钟阅读

一轮实际审查里，测试、Lint 和启动检查都通过，调度窗口、状态文件和失败 Promise 仍然藏着可复现的问题。

我让 Codex 检查一个由桌面壳、控制服务和任务执行端组成的工具。要求很明确：先确认问题是否存在。初始测试、Lint 和启动自检都通过，但后续审查仍找到了多处现有测试没有覆盖的边界。

来自真实只读审查记录。本文只保留通用技术现象，不公开项目、账号、执行地址和业务任务。

从边界交接处开始

一个执行脚本把 Node 路径当作必需参数，调用它的两个 runner 却都没有传入。单独看脚本与 runner，它们各自都容易被认为合理；沿着真实调用链连起来，任务会在进入业务代码之前直接失败。

另一个状态文件允许根对象成功解析，但没有验证数组中的每个元素。{"tasks":[null]} 是合法 JSON，却会在启动遍历时访问 task.status 并抛出异常。语法校验通过，从来不能代替结构校验。

留意被永久记住的失败

let loading;

function loadRuntimeConfig() {
    if (!loading) {
        loading = requestConfig().catch((error) => {
            loading = null;
            throw error;
        });
    }
    return loading;
}

原问题是一次 IPC 请求被缓存为 Promise，首次超时后缓存一直指向 rejected Promise，所有后续请求都会立即失败。示例展示失败后释放缓存的基本做法；实际系统还需要考虑重试间隔、取消以及配置有效期。

把每个结论写成可复核的句子

对我有用的审查格式是：触发输入、实际执行路径、错误结果、影响范围、验证方式。仅仅写“这里可能有竞态”还不够；需要说明哪两个动作交错、哪个状态被覆盖，以及为什么现有锁或事务拦不住。

记录中区分了实际复现、代码路径确认和环境未完成的检查。例如依赖审计遇到注册表服务错误，就没有把依赖是否安全当成已经验证的结论。文章保留这种边界，比把所有检查都写成通过更有价值。
