加了五分钟随机抖动，定时任务却跳到了明天

SLLYING2026.09.084 分钟

调度器同时过滤基准时间和抖动后的执行时间，在两者之间形成了一个被跳过的窗口。测试全绿，也可能漏掉这一类时间边界。

一次只读代码审查发现，调度器为了给固定时刻加入随机抖动，同时检查了基准时间和最终执行时间是否在当前时间之后。看似更严谨的条件，恰好跳过了本该执行的候选。

根据 Codex 实际审查结论整理。原任务只验证问题，没有修改业务代码；下方修正和测试输入是本文的缩小示例。

错误条件如何吞掉今天的任务

假设今天的基准时间是 10:00，随机偏移是 +3 分钟，所以实际执行时间为 10:03。当系统在 10:01 计算下一次触发时，这个任务仍在未来，应当被选中。但 baseMs > afterMs 已经不成立，算法于是考虑下一天。

// baseMs = 10:00, candidateMs = 10:03, afterMs = 10:01
if (baseMs > afterMs && candidateMs > afterMs) {
    return candidateMs;
}

最终是否在未来，应该由真正的候选执行时间决定。不过仅仅删去前半个条件还不够：候选集合也必须覆盖那些基准时间已过去、但正抖动尚未到达的情况。跨日的负抖动则需要检查下一天的基准候选。

把随机数变成可以重放的输入

function candidateAfter(baseMs, jitterMs, afterMs) {
    const candidate = baseMs + jitterMs;
    return candidate > afterMs ? candidate : null;
}

const minute = 60_000;
const ten = Date.UTC(2026, 0, 1, 10);
console.assert(candidateAfter(ten, 3 * minute,
    ten + minute) === ten + 3 * minute);

测试时直接注入偏移量，生产时再由独立策略生成。一次调度候选的抖动应当稳定，否则每次刷新状态都重新抽签，任务时间会来回变化。

除了整点，还需要测试什么

  • 当前时间位于基准时间与候选时间之间。
  • 当前时间恰好等于候选时间，明确是否允许立即执行。
  • 正负抖动跨过午夜，或者跨过星期边界。
  • 带时区的日历任务经过夏令时切换。

审查记录报告已实际复现跳过当天触发的问题，同一轮现有测试仍全部通过。这不是测试没有价值，而是测试样本没有包含这个具体窗口。修复时应把窗口本身固化成回归输入。
