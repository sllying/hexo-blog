Java 三层架构：从一个用户查询理解职责边界

SLLYING2025.05.243 分钟

Controller、Service、Repository 的区别不在文件夹名称，而在它们各自处理什么变化。用一个查询用例把输入、规则与存储分开。

这是旧站 Java 主题的重新整理。三层架构的价值，是让 HTTP、业务规则和数据存储各自变化时，不必一起修改整个调用链。

先看一个有真实职责的查询

@GetMapping("/users/{id}")
public UserView getUser(@PathVariable long id) {
    return userService.getVisibleUser(id);
}

public UserView getVisibleUser(long id) {
    User user = userRepository.findById(id)
        .orElseThrow(UserNotFoundException::new);
    visibilityPolicy.check(user);
    return UserView.from(user);
}

Controller 负责输入和 HTTP 出口；Service 组合“查询可见用户”这个用例；Repository 负责持久化细节。示例省略了构造器和类声明，异常到 HTTP 状态码的映射可以由统一异常处理器完成。

边界不是多放几个空壳类

如果 Service 只把参数原样转交给 Repository，它可能暂时只是一个很薄的用例入口。这并不意味着必须人为加复杂度。真正重要的是业务规则出现后有明确归属，而不是让 Controller 直接执行数据库查询和权限判断。

返回值和事务也要选择边界

不要直接把数据库实体当作所有 API 的返回契约，尤其是实体包含敏感字段或懒加载关系时。多个写操作必须一起成功的用例，通常在 Service 处确定事务范围；只给每个 Repository 方法单独开事务，不能保证整个用例原子完成。

测试怎么分工

Service 测规则和结果，Repository 测真实查询与数据库约束，Controller 测请求绑定和错误响应。不要让三层都重复同一个“返回非空”断言；各层测试应该证明自己的责任。
