资源调研里，链接、说明和实测分别能证明什么

SLLYING2026.09.082 分钟

整理资源项目时，我更关心一项结论是从哪里来的。官方文档、仓库实现和本机实验各有证明范围，不能互相替代。

我曾让 Codex 对一个资源研究项目做整体总结。能读取到的任务摘要说明了项目梳理范围，但没有逐条保留资源验证过程。因此，这篇记录方法，不把没有证据的推荐写成实测结果。

把每项结论绑到具体来源

“支持某功能”可能只是 README 的声明；“可以安装”可能只代表依赖安装成功；“当前环境能完成目标任务”才需要实际输入与输出。报告里应该保留这三种状态，让读者知道自己还需要验证什么。

{
  "capability": "offline inference",
  "documentation": "declared",
  "sourceInspection": "partial",
  "runtimeTest": "not-run",
  "version": "pinned-for-review"
}

许可证和运行条件一起记录

仓库开源不意味着模型权重、示例媒体和托管服务采用同一条款。版本、运行平台、硬件条件、依赖来源和已知失效条件也会影响结论。尤其是免费额度、在线服务权益和模型可用性，不能把旧截图当作当前保证。

让“不确定”成为可执行的下一步

不要只写“有待确认”。写清是缺少模型权重、目标平台没有安装环境，还是上游文档与实现不一致。下一次继续调研时，就能直接补上那项证据，不必再重复收集链接。

# 技术调研# 开源# 证据
