数据库发布被拦住：SQL 文件哈希为什么不是结构指纹

SLLYING2026.09.084 分钟

一次正常的基线重新导出让生产发布持续失败。排查发现，守卫混淆了文件变化与结构变化，基线记录又只在首次建库时写入。

这次发布失败不是一句“哈希不一致”就能解释的。Claude Code 的排查记录里，发布守卫比较的是 SQL 转储文件的 SHA-256，而开发规范又要求每次数据库变化后重新导出基线。

根据真实数据库发布排障整理。表名、版本号、环境名称和摘要值已省略；SQL 只展示结构抽取的一个局部。

文件字节变了，不等于数据库结构变了

转储可能因为 AUTO_INCREMENT、导出顺序或工具生成内容不同而改变字节。对整个文件求哈希，回答的是“这两个文件是否逐字节相同”，不是“两个数据库能否运行同一版本的应用”。

这次任务确实也包含一条未应用的结构迁移，因此不能靠放宽守卫直接通行。需要把真实结构差异和无害导出差异分开，再决定是否允许发布。

对需要保持一致的结构建立确定表示

SELECT table_name, ordinal_position, column_name,
       column_type, is_nullable, column_default,
       extra, generation_expression, collation_name
FROM information_schema.columns
WHERE table_schema = DATABASE()
ORDER BY table_name, ordinal_position;

上面只是列定义的一部分。真实的结构指纹还要覆盖表引擎、字符集、索引、约束、外键、触发器等项目需要的对象，固定排序与 NULL 编码后再计算摘要。不要直接对随机顺序的查询输出求哈希，也不要把行数、基数、更新时间这种运行状态混入判据。

原任务采用了目标初始化库和运行库分别计算结构指纹的办法。数据库版本和会话参数也要一致，否则不同版本对默认值或表达式的格式化差异会带来新的误报。

第二个错误藏在基线记录里

旧记录只在首次建库时写入，迁移和发布成功后不推进。结果是数据库已经向前走，守卫却一直拿初始化时的值比较。新的流程在成功发布后记录目标基线，并用临时文件替换的方式避免留下半写入状态。

检查放在什么时候，同样影响可靠性

原守卫在重建数据库容器之后才执行，拒绝发布本身也引起了服务变更。改动把可以只读完成的检查前置，在真正变更运行状态前发现不一致，并在变更后再次校验结构。

前置检查防止明显不满足条件的发布产生副作用，后置检查确认实际运行状态与发布目标一致，两者回答不同的问题。

已知的验证范围

记录中有 Shell 契约检查、ShellCheck 和 MySQL 8.0 上重复计算得到一致指纹的结果。这个证据支持 SQL 可执行且在该环境里稳定；不能由此推断跨 MySQL 大版本、所有存储过程或任意字符集组合都已经覆盖。
