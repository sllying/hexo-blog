Excel 导出为什么出现了内部枚举：修复应放在哪一层

SLLYING2026.09.083 分钟阅读

后台显示“校内 / 校外”，下载的模板却是 SCHOOL、MAJOR、DISTRICT。问题在导出表达，贸然改公共查询会影响另一个使用者。

这次导出问题并不难描述：页面里的组织类型已经合并为“校内 / 校外”，Excel 模板还在展示七种内部层级编码。难点是选对修复位置。

根据 Claude Code 的真实实现记录整理。真实组织、账号、提交和部署环境已移除，枚举只保留与问题有关的技术含义。

先追到单元格是在哪里写出来的

生成模板的方法直接把查询结果的 deptType 写进单元格。这个字段来自内部组织层级，页面上看到的两类归属则经过了业务映射。文件格式正确、SQL 也返回正确数据，但导出给用户的语义不对。

如果第一反应是把 SQL 的字段统一改成中文，另一个使用这条查询的注册接口就会失去原始类型，进而影响校内外筛选。共享数据读取和某个具体出口的展示，是两个需要分别确认的边界。

在导出边界做明确转换

String labelForExport(DeptType type) {
    return switch (type) {
        case SCHOOL, MAJOR, CLASS -> "校内";
        case DISTRICT, STREET, COMMUNITY, ORGANIZATION -> "校外";
    };
}

示例刻意使用穷举的枚举分支，让新增类型时编译器提醒补齐规则。原实现还按既有业务约定处理了未知类型；在新系统里，是否兜底、是否标记待确认，需要根据业务决定，不能把任意脏数据静默当作正常分类。

测试应该读回最终文件

单测只调用映射函数，能证明映射正确，却无法证明模板真的调用了它。因此原任务新增的测试会实际生成工作簿，再读回“组织类型”单元格，覆盖所有已知类型和既定兜底分支。

这类测试还能发现列索引移动、标题调整、类型写错等出口问题。与此同时，保留接口层测试，确认共享查询仍然输出原始编码。

结果与边界

记录中有 Maven 验证通过，以及测试环境实际导出前后对比。修复发生在模板生成处，没有改动共享 SQL。这个例子留下的判断很实用：用户看到的字段不对，先定位最终展示边界，再决定是否需要改变整个数据契约。
