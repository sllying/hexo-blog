Claude Code 说已经完全离线，我为什么还要继续验证

SLLYING2026.09.083 分钟阅读

网络拦截、本地 Mock API 和大量媒体文件让静态分析得出了乐观结论，实际运行却暴露出缺失资源、错误路由和 Worker 初始化问题。

同一个离线化任务，让我看到了“分析已经完成”和“用户能正常使用”之间的差距。Claude Code 先检查了网络拦截、本地 API 和媒体目录，给出了应用已经完全本地化的结论。

本文对照了本地 Claude Code 分析记录和后续 Codex 执行记录。它们反映任务推进时的状态，不把两次记录视为同一时刻的对照实验。

初步证据都是真的，结论却走得太远

目录里确实存在大量音视频，自定义协议和请求拦截也已经存在。这些证据能说明项目采用了离线化方案，却不能直接证明全部课程资源齐全、每条生产路由正确，或模型能够在目标运行时真正初始化。

“没有找到某功能”也只能报告搜索范围和当前发现。把它写成需求不存在，会直接跳过用户需要的验证。

后续执行发现了什么

  • 严格资源审计仍报告真实缺失媒体，文件总量不能代替引用闭包。
  • 本地分支打开了旧调试路由，需要检查实际进入的课程页面。
  • Worker 脚本能够读取，不代表目标 Electron 能从该协议启动 Worker。
  • 从独立发布目录复制启动，需要再验证资源解析和本地数据路径。

我现在会追问证据的层级

静态扫描证明声明和文件关系；构建证明打包流程能走通；启动冒烟证明主路径能运行；断网下的功能验收才接近“离线可用”。这几个层级都值得保留，也必须分别表述。

[已确认] 目标文件在发布包中
[已确认] 应用能够启动到指定页面
[待验证] 每个课程都能完成核心交互
[阻塞]   引用清单中仍缺少原始媒体

后续记录还有对“Worker 可访问”的进一步纠正：必须等待初始化结果，不能只检查资源响应。复盘里最值得保留的，正是这种结论被新证据修正的过程。
