Electron 离线化：文件都在，为什么 Worker 还是起不来

SLLYING2026.09.084 分钟

离线包里的 ONNX 文件可读，Worker 初始化却超时。真正需要检查的是目标 Electron 运行时中的协议、WASM 解析与消息握手。

离线化一个 Electron 应用时，我遇到的关键反例是：模型文件能读、Worker 脚本也能响应，却无法完成实际初始化。资源存在性检查已经通过，运行链路仍然断着。

根据真实执行记录整理。自定义协议、应用名称和资源标识已泛化；代码为用于说明验证方式的示例。

把“能请求”与“能执行”分开

后续诊断在目标 Electron 13 中比较了不同 Worker 来源：data URL 可以创建，项目自定义协议与 file URL 的目标用法却没有正常启动，表现为等待初始化结果超时。这个结论属于那次运行时和配置，不能扩展成所有 Electron 都不支持自定义协议 Worker。

function waitForReady(worker, timeoutMs = 5000) {
    return new Promise((resolve, reject) => {
        const cleanup = () => {
            clearTimeout(timer);
            worker.removeEventListener("message", onMessage);
            worker.removeEventListener("error", onError);
        };
        const onMessage = ({ data }) => {
            if (data?.type !== "ready") return;
            cleanup();
            resolve(data);
        };
        const onError = (event) => {
            cleanup();
            reject(new Error(event.message || "Worker failed"));
        };
        const timer = setTimeout(() => {
            cleanup();
            worker.terminate();
            reject(new Error("Worker initialization timed out"));
        }, timeoutMs);
        worker.addEventListener("message", onMessage);
        worker.addEventListener("error", onError);
    });
}

示例要求 Worker 在依赖和模型初始化完成后主动发送 ready，而不是一进入脚本就发送。否则握手只能证明脚本开始执行，依然不能证明推理能力可用。

锁定 Worker 与 WASM 的版本关系

任务中的修复方向是由构建阶段生成同版本的内嵌 Worker 与 WASM 资源，消除运行时跨协议和相对路径依赖。这种兼容方案需要检查 CSP、资源体积和目标运行时；能升级 Electron 时，也应该评估升级后的标准加载方案。

离线验收还缺不了资源闭包

与此同时，严格审计仍发现真实缺失的原始媒体。界面启动、Worker 初始化和资源齐全必须分别报告。便携发布包还应复制到一个新的目录启动，验证路径迁移、本地存储、视频 Range 请求和外部请求处理。

这篇复盘最重要的边界是：修好一段执行链路，并不等于整个离线产品已经完整交付。缺少媒体时，应该准确列出缺项，不能用占位文件制造完成感。
