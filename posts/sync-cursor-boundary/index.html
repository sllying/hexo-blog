Push 成功后，为什么另一台设备的记录消失了

SLLYING2026.09.084 分钟阅读

把 Push 响应里的服务端游标直接保存为 Pull 游标，会跳过尚未拉取的其他设备变更。写入确认与读取进度，需要表达不同的事实。

在一个本地优先学习工具的同步实现中，Codex 记录了一处会漏同步的缺陷：客户端提交本地修改成功后，直接用响应里的服务端游标覆盖本地 Pull 游标。

根据真实实现记录整理。下面的设备名称、序号和代码是为了展示状态变化而重建的最小示例，不是用户数据。

用三个序号就能复现这个错误

  1. 设备 A 已拉取到服务端变更 10，因此本地 Pull 游标为 10。
  2. 设备 B 提交了一条修改，服务端产生变更 11。
  3. 设备 A 提交本地修改，服务端产生变更 12，Push 响应返回服务端当前序号 12。
  4. A 把 Pull 游标设为 12，下次只请求 12 之后的修改，于是永远错过 B 的变更 11。

Push 成功只证明自己的修改被接受，无法证明 10 到 12 之间的所有变化都已经应用到本地。游标都是数字，并不意味着它们有相同语义。

让状态字段各自说清一件事

const receipt = await api.push(pendingChanges);
await markAcknowledged(receipt.acceptedIds);

const page = await api.pull({ after: state.pullCursor });
await database.transaction(async () => {
    await applyRemoteChanges(page.changes);
    await savePullCursor(page.nextCursor);
});

示例中的 Push 确认只清理已确认的待提交项。Pull 游标只能由一次成功应用的 Pull 批次推进，并与该批次的数据变更一起提交。若数据写入失败，游标也必须回滚；否则下一次重试同样会跳过数据。

回归测试要包含两台设备

只测试“修改、上传、收到成功”很难发现这个问题。需要固定服务端变更顺序，让 A 拉取后暂停，B 上传，再让 A 上传并拉取。断言重点是 A 最终包含 B 的修改，以及重复 Pull 不会重复生成记录。

还应检查分页中断、上传重试、删除标记、账号切换。尤其是游标要绑定账号和数据集，不能把上一个账号的读取位置带给下一个账号。

验证边界

原任务记录明确指出并修正了 Push 游标覆盖 Pull 游标的问题。本篇提炼的是这个确定的语义错误；它没有证明系统的冲突合并、离线删除或所有异常恢复已经完整正确，这些仍需要各自的测试证据。
