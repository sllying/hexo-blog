返回 200，却打开了另一个站点：一次 Nginx 子路径排障

SLLYING2026.09.084 分钟阅读

子应用容器正常，访问入口却跳到另一个系统的登录页。真正的问题藏在被部署覆盖的代理规则，以及仍然新鲜的浏览器缓存里。

这次和 Claude Code 排查的是一个很容易看错的问题：子应用明明在运行，打开入口却进入了另一个系统的登录页。HTTP 状态码始终是 200，让问题看起来像前端路由出错。

根据 2026 年 8 月的真实排障记录整理。应用名、域名、部署目录和提交标识已替换；以下配置为说明问题的缩小示例。

先确认 200 返回的到底是什么

直接访问子应用服务时，页面标题和资源都正确。经过共享代理访问时，请求拿到的却是主站的 HTML：正文标题、长度和 ETag 都与主站一致。随后主站的 JavaScript 执行登录守卫，浏览器才跳到登录页。

这一步把两个现象分开了：服务器返回错误的应用文档，前端路由再对这份文档执行了正确的登录逻辑。只盯着 200，或者只查看地址栏最后的登录地址，都会错过第一个错误。

消失的规则来自一次正常部署

服务器上的子路径 location 已经不在了。部署脚本会把仓库里的 Nginx 配置完整覆盖到服务器，而上一次子路径接入只修改了服务器文件。下一次主站部署时，那次手工修复自然被覆盖。

location = /lab {
    return 308 /lab/;
}

location /lab/ {
    proxy_pass http://127.0.0.1:8090/;
}

这里 proxy_pass 尾部的斜杠会去掉匹配到的 /lab/ 前缀。这个写法只适用于上游按根路径提供资源的情况；如果上游本身部署在同名子路径，转发策略要一起调整。前端构建的资源 base 和路由 base 也必须对应。

修复落进了部署实际使用的仓库配置，并进入同一套 nginx -t 校验。这样配置与发布流程具有同一个来源，后续部署才能重现这次修复。

服务恢复了，浏览器为什么还没恢复

代理修好后，命令行拿到正确页面，原浏览器仍旧进入登录页。起初怀疑 Service Worker，但所谓的 sw.js 请求返回 text/html，只是 SPA 的兜底页面；前端也没有注册 Worker 的代码。这条假设因此被排除。

剩下的证据指向 HTTP 缓存：旧 HTML 有 Last-Modified 和 ETag，却没有明确的 Cache-Control。浏览器可以依据启发式新鲜度直接使用旧副本，连条件请求都不发送。带新查询参数的入口、禁用缓存后重载，是区分缓存与服务器响应的便捷办法。

# HTML 入口：可以保存，但复用前需要验证
Cache-Control: no-cache

# 文件名含内容哈希的静态资源
Cache-Control: public, max-age=31536000, immutable

这次验证覆盖到哪里

记录中确认了代理入口返回目标应用、脚本与模型资源正常响应，共享代理上的其他入口也经过检查。缓存问题的判断有响应头和不同客户端行为支持；文章里的缓存头是归纳出的配置建议，不把它写成当时已经部署的结果。

下一次看到“200 但页面不对”，先比较响应正文、Content-Type 和入口归属，再排查前端路由。
